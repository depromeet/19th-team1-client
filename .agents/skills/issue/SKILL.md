# 이슈 먼저

이 레포의 흐름은 **이슈 → 작업 → PR(`close #번호`) → `dev` 병합 때 이슈가 저절로 닫힘**이다(결정 기록 0006).

**부르는 때** — PR 로 끝나는 변경(코드 · 문서 · 설정)을 요청받았을 때, 작업을 시작하기 전에.
**부르지 않는 때** — 질문·조사만 하는 요청, 이미 열린 PR 의 리뷰 반영 · `rebase-dev`, 배포 PR(`pr-main`), 사람이 이슈 번호를 준 경우(그 번호를 쓴다).

1. **같은 작업이 있나** — 열린 이슈에서 찾는다. 같은 일이면 그 번호를 쓰고 새로 만들지 않는다(세션을 여러 개 돌려도 이슈가 겹치지 않게).
   ```bash
   gh issue list --state open --search "<핵심 낱말>"
   ```
2. **양식** — `.github/ISSUE_TEMPLATE/` 에서 고른다: 새 기능·개선은 `feat.yml`, 의도와 다르게 동작하는 것은 `fix.yml`, 리팩터링·문서·설정·테스트는 `task.yml`. 양식 파일을 읽고 칸 제목(`label`)을 `### 제목` 으로 그대로 쓴다 — 양식 이슈는 `gh issue create` 가 칸을 채워 주지 않는다.
   - feat · task 양식: `### 무엇을 · 왜` · `### 할 일` · `### 참고 자료`
   - fix 양식: `### 현상` · `### 재현 방법` · `### 기대 동작` · `### 환경`(웹 · 앱 (iOS) · 앱 (Android) · 여러 곳 중 하나) · `### 스크린샷`
3. **본문** — 요청·자료에 있는 내용만 쓴다. 받은 내용에 없는 칸은 `없음`.
   - "할 일"은 이번 작업의 계획을 체크리스트(`- [ ]`)로.
   - 기능이면 "참고 자료"에 PRD 요구사항 ID(`C·O·H·R·N·P-번호`)와 디자인 링크.
4. **라벨** — 작업 브랜치의 type 과 같게: `feat` · `fix` · `refactor` · `style` · `docs` · `chore` · `test`. 그 밖의 type(`ci` · `build` · `perf` · `revert`)은 `chore`.
5. **만들기** — 제목은 한국어 한 줄로 무엇을 하는지.
   ```bash
   gh issue create --title "<무엇을>" --body-file <본문> --label <type> --assignee @me
   ```
6. **이어서** — 이슈 번호를 들고 작업한다. PR 을 올릴 때 `pr-dev` 가 "관련 이슈" 칸에 `close #번호` 를 적는다.
7. **보고** — 이슈 링크(새로 만들었는지, 있던 것을 썼는지).
