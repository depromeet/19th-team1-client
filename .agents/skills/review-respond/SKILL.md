# 리뷰 대응

규칙은 `docs/code-review.md`. 핵심: 반영은 로컬 커밋으로, 스레드마다 답글, resolve 는 리뷰어(Claude 스레드는 작성자).
답글 첫 단어가 리뷰 사례가 된다 — 기준 관리자가 주마다 모아 기준을 고친다(`docs/code-standards.md` "기준이 쌓이는 길").

1. **모으기** — 안 닫힌 스레드만.
   ```bash
   gh api graphql -f query='query($o:String!,$r:String!,$n:Int!){repository(owner:$o,name:$r){pullRequest(number:$n){reviewThreads(first:100){nodes{isResolved path line comments(first:20){nodes{author{login} body url}}}}}}}' -F o=depromeet -F r=19th-team1-client -F n=<번호>
   ```
2. **검증** — 스레드마다 지적한 코드를 실제로 열어 본다. 지적이 맞는지 코드로 판단한다. Claude 지적도 틀릴 수 있다 — `[결함]` 이면 적힌 예시 입력을 실제로 따라가 본다(시험 · 명령으로 재현할 수 있으면 재현한다).
3. **분류표** — 사람에게 보여 준다. 사람이 "다 반영해"라고 미리 말했으면 추천대로 하고, 아니면 고르게 하고 멈춘다.

   | #   | 누가 | 파일:줄 | 지적 한 줄 | 판단 | 추천 |
   | --- | ---- | ------- | ---------- | ---- | ---- |
   - 판단: `맞음` · `일부 맞음` · `틀림(근거)` · `취향`
   - 추천: `반영` · `반영 안 함(이유)` · `보류(언제)` · `질문으로 답`
   - `[필수]` 를 반영하지 않을 때는 근거가 특히 필요하다.

4. **반영** — 고른 것만 고친다. 스레드 하나 또는 관심사 하나 = 커밋 하나(`fix: 리뷰 반영 — <무엇>`). GitHub suggestion 버튼은 쓰지 않는다.
   코드를 고쳤으면 바뀐 워크스페이스의 `lint` · `typecheck` · 관련 테스트를 돌린다. 푸시는 사람이 시킬 때. 푸시하면 Claude 가 추가 커밋분만 다시 리뷰한다.
5. **답글 초안** — 스레드마다, **첫 단어를 셋 중 하나로**(사례를 모을 때 이 단어로 센다):
   - `반영:` 커밋 해시 + 한 줄
   - `반영 안 함:` 이유 한 줄 — Claude 지적이 틀렸으면 왜 틀렸는지(이게 리뷰어를 고치는 사례가 된다)
   - `보류:` 언제 · 어디서(이슈 번호)

   게시하지 않고 초안만 준다.

6. **같은 지적이 두 번째면** — 이 PR 이나 앞 PR 에서 같은 종류의 지적이 있었으면 답글 초안 끝에 `기준 후보` 한 줄을 붙인다. 장부에 올릴지는 기준 관리자가 정한다.
