# 커밋

커밋은 사람이 시킬 때만 한다.

1. `git status --short` 와 `git diff` 로 바뀐 파일을 본다. 파일마다 **이번 작업인지** 가른다.
   이번 작업이 아닌 파일(다른 작업의 변경, 생성물, 실험 파일)은 커밋하지 않고 보고에 적는다.
2. 코드를 고친 작업이면 `self-review` 를 먼저 돌렸는지 본다. 안 돌렸으면 돌린다.
3. 관심사별로 나눈다. 한 커밋 = 리뷰어가 한 번에 이해할 한 가지 변경. 기능 변경과 정리(이름·순서)는 나눈다.
4. 메시지는 `commitlint.config.mjs` 규칙을 따른다: `<type>(<scope>): <한글 내용>`.
   - type: `feat fix refactor style docs chore test ci build perf`
   - scope: `web` · `mobile` · `shared` 등 바뀐 워크스페이스. 여러 곳이면 생략
   - 본문에는 **왜**를 적는다. 무엇을 바꿨는지는 diff 가 보여 준다.
5. 파일을 골라 올린다 — `git add <파일>`. `git add -A` · `git add .` 는 1번에서 가른 결과가 전부 이번 작업일 때만.
6. 커밋 훅(lint-staged · commitlint)이 실패하면 원인을 고치고 **새로** 커밋한다. `--no-verify` 로 건너뛰지 않는다(훅이 막는다).
   훅이 파일을 고쳤으면 그 변경도 같은 커밋에 넣는다.
7. 막히면(훅이 계속 실패, 이번 작업인지 애매한 파일) 멈추고 보고한다.

보고: 커밋마다 해시 앞 7자리와 제목, 커밋하지 않고 남긴 파일과 이유.
