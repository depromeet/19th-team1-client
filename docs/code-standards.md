# 코드 기준 장부

웹·앱 코드의 기준을 번호(`C-xx`)로 모은다. 에이전트는 바뀐 파일에 맞는 번호를 대조하고,
리뷰어는 코멘트에 번호를 인용한다 — `[제안] C-17 로딩은 위에서 끊어 주세요`.

**지금은 전부 `초안`이다.** 팀원이 처음부터 기준을 만들기 어려워서 일반적인 원칙과 정해진 스택 몫을 먼저 적었다.
리뷰에서 항목마다 동의·반대를 달고, 동의한 것은 `확정`으로 바꾼다. 반대가 있으면 고치거나 `폐기`한다.

## 읽는 법

| 칸          | 값                                                                                                                       |
| ----------- | ------------------------------------------------------------------------------------------------------------------------ |
| 상태        | `초안` 적용하되 보고에 "초안 기준" 표시 · `확정` 팀이 정함 · `폐기` 인용 금지(기록은 남김)                               |
| 걸리는 방식 | `기계` ESLint·훅·CI 가 막음 · `기계`(일부) 일부만 막고 나머지는 판단 · `예시` 따라 쓸 코드가 있음 · `글` 문장으로만 있음 |
| 예시        | 레포에 모범 파일이 있으면 그 경로, 아직 없으면 짧은 좋은/나쁜 코드 조각                                                  |

목표는 `글` → `예시` → `기계` 로 올리는 것이다. 기계로 올라간 기준은 룰 문장(`.claude/rules/*.md`)에서 지운다.
판단이 필요해 기계가 못 막는 기준은 `글` 에 머무는 게 정상이다.
번호 없이 기계만 막는 것도 있다 — `@ts-ignore`(`ban-ts-comment`) · import 순서 · `console.log`(`no-console`). 린트 메시지로 충분해 번호를 두지 않는다.

**에이전트는 룰 문장보다 옆 코드를 더 따라 쓴다.** 그래서 긴 설명은 이 장부와 모범 코드에 두고, 경로별 룰은 번호와 한 줄만 둔다.
아직 기능 코드가 적어 지금은 코드 조각으로 예시를 든다. 첫 기능 PR 이 병합되면 그 파일을 모범으로 삼아 `예시` 를 경로로 바꾸고 조각은 지운다 —
첫 기능 PR 은 이 장부 기준으로 특히 꼼꼼히 리뷰한다.

## 기준을 더하거나 바꿀 때

- 장부를 고치는 PR 을 올린다. 새 항목은 `초안` 으로 넣고, 팀 리뷰에서 `확정` 한다. 리뷰에서 기준을 키우는 절차는 리뷰 흐름에서 정한다.
- **같은 PR 에서 짝도 고친다** — 경로별 룰 색인(`.claude/rules/*.md`)의 그 번호 줄, 기계로 올렸으면 `AGENTS.md` 의 "기계가 막는 것" 목록. 한쪽만 고치면 Codex 처럼 색인만 읽는 에이전트가 옛 기준을 따른다.
- 번호는 다시 쓰지 않는다. 뒤집으면 새 번호를 만들고 옛 번호에 `대체됨: C-xx` 를 붙인다.
- 그때만의 취향은 올리지 않는다. "다음에도 같은 지적을 할 것인가"가 기준이다.
- 항목 모양: `### C-xx 한 줄 기준 · 상태 · 걸리는 방식` 아래에 `기준` · `왜` · (있으면) `예시` · `기계` · `출처`(PR 번호) · `날짜`. 출처·날짜는 `확정` 할 때 채운다.

## 타입

### C-01 `any` 를 쓰지 않는다 · `초안` · `기계`

- 기준: 모르면 `unknown` + 좁히기, 범용이면 제네릭.
- 왜: `any` 는 그 값이 닿는 곳의 타입 검사를 끈다.
- 기계: `@typescript-eslint/no-explicit-any`

### C-02 non-null 단언(`!`)을 쓰지 않는다 · `초안` · `기계`

- 기준: 기본값 · early return · 분기로 "없을 때"를 드러낸다.
- 왜: `!` 는 "여기선 없을 리 없다"는 가정을 숨겨, 가정이 깨질 때 화면에서 터진다.
- 기계: `@typescript-eslint/no-non-null-assertion`

### C-03 이중 단언(`as unknown as T`)을 쓰지 않는다 · `초안` · `기계`

- 기준: 맞는 타입을 만들거나 타입 가드·스키마 파싱으로 좁힌다.
- 왜: 타입 검사를 통째로 건너뛴다. 테스트 데이터에 쓰면 응답이 바뀌어도 테스트가 초록으로 남는다.
- 기계: `no-restricted-syntax` (`packages/eslint-config/base.mjs`)

### C-04 옵셔널(`?`)은 최후 수단이다 · `초안` · `글`

- 기준: 기본값 → 의미 있는 빈 값 → 판별 유니온 순서로 먼저 시도한다. 없을 수 있는 값은 경계에서 한 번 처리한다.
- 왜: 타입 에러를 피하려고 붙인 `?` 는 안쪽 모든 곳에 `?.` · `??` 를 퍼뜨리고, 진짜로 없는 경우와 구분이 안 된다.
- 예시:
  ```ts
  // 나쁨 — 없는 경우와 아직 안 정한 경우가 섞인다
  interface LooseFilter {
    keyword?: string;
    tags?: string[];
  }
  // 좋음 — 의미 있는 빈 값
  interface Filter {
    keyword: string;
    tags: string[];
  } // 빈 문자열·빈 배열이 "조건 없음"
  ```

### C-05 단언(`as`)은 좁힐 방법이 없을 때만, 이유 주석과 함께 · `초안` · `글`

- 기준: 타입 가드·스키마로 좁힐 수 없을 때만 쓰고 왜 안전한지 적는다.
- 왜: 이유 없는 단언은 리뷰어가 안전한지 판단할 수 없다.

### C-39 객체 모양은 `interface`, 유니온·함수·조합은 `type` · `초안` · `기계`

- 기준: Props 같은 객체 모양은 `interface`. 유니온 · 함수 타입 · `z.infer` · 유틸리티 타입 조합은 `type`. 서버 응답은 손으로 쓰지 않고 스키마에서 꺼낸다(C-51).
- 왜: 같은 모양을 두 방식으로 섞어 쓰면 리뷰 때마다 어느 쪽인지 묻게 된다.
- 기계: `@typescript-eslint/consistent-type-definitions`

### C-40 ESLint 규칙을 끌 때는 이유를 같은 줄에 · `초안` · `글`

- 기준: `// eslint-disable-next-line <규칙> -- <왜 안전한가>`. 파일 전체 끄기(`/* eslint-disable */`)는 쓰지 않는다.
- 왜: 막는 규칙이 많을수록 끄는 길이 늘어난다. 이유가 없으면 리뷰어가 예외인지 실수인지 모른다.
- 기계 후보: `eslint-comments/require-description` — 끄는 주석이 늘면 올린다.

## 배치 · 구조

### C-06 새 코드는 기능 폴더 안에 먼저 둔다 · `초안` · `글`

- 기준: `src/features/<도메인>/` 에 두고, 두 기능 이상이 **실제로** 같이 쓰게 되면 `src/lib` · `src/components` 로 올린다.
- 왜: 미리 공용으로 빼면 한 곳에서만 쓰는 코드가 공용 폴더에 쌓이고, 고칠 때 영향 범위가 안 보인다.

### C-07 순수 함수는 기능 폴더의 `utils.ts` 하나에 모은다 · `초안` · `글`

- 기준: 함수 하나짜리 파일을 만들지 않는다. 테스트는 `utils.test.ts` 하나. 파일이 커지면 기능 폴더를 나눈다.
- 언제 빼나: 테스트할 가치가 있거나(분기·계산) 읽기가 나아질 때. 한 줄 변환은 쓰는 자리에 둔다.
- 예외: 한 모듈(예: API 클라이언트)만 쓰는 변환은 그 모듈 파일에 둬도 된다. 기반 코드(`src/lib/*`)는 처음부터 공용이라 C-06 의 "기능 폴더 먼저"를 따르지 않는다.
- 왜: 함수마다 파일을 만들면 같은 함수가 이름만 바꿔 또 생긴다.
- 예시: `apps/web/src/lib/api/client.ts` (모듈 전용 변환을 그 파일 안에 둠)

### C-08 유틸을 새로 만들기 전에 있는 것을 찾는다 · `초안` · `글`

- 기준: 기능 폴더 `utils.ts` → `src/lib` 순으로 찾는다. 같으면 쓰고, 출력만 다르면 옵션을 더하고, 동작이 다르면 이름을 구분한다.
- 왜: 날짜 포맷처럼 비슷한 함수가 여러 개 생기면 화면마다 표기가 갈라진다.

### C-09 상위 폴더는 `@/` 절대 경로로 가져온다 · `초안` · `기계`

- 기준: 같은 폴더(`./`)만 상대 경로, 위는 `@/`.
- 왜: `../../` 는 파일을 옮기면 깨지고 어디서 왔는지 안 보인다.
- 기계: `no-restricted-imports`

### C-10 `export *` 를 쓰지 않는다 · `초안` · `글`

- 기준: 다시 내보낼 때는 이름을 골라서. 묶음 `index.ts` 는 도메인 경계에서만.
- 왜: 무엇이 밖으로 나가는지 안 보이고, 쓰지 않는 코드까지 번들에 딸려 온다.

### C-11 경로 문자열을 직접 쓰지 않는다 · `초안` · `글`

- 기준: 화면 경로는 상수 한 곳에서 꺼낸다. 새 화면은 상수부터 더한다.
  경로·쿼리 키·응답 필드를 바꾸면 그것을 쓰는 곳 — 쿼리 키 함수와 무효화, 화면 이동 링크, (생기면) 접근 가드 — 을 같은 PR 에서 함께 고친다. 바꾸기 전에 이름으로 쓰는 곳을 검색한다.
- 왜: 경로를 바꿀 때 문자열 검색으로 빠짐없이 찾을 수 없다.

### C-12 환경 변수는 `@/lib/env` 에서 꺼낸다 · `초안` · `기계`

- 기준: `process.env` 를 직접 읽지 않는다. 새 변수는 `env.ts` 스키마와 `.env.example` 에 함께 더한다.
- 왜: 빠진 값을 화면이 아니라 시작할 때 알게 한다.
- 기계: `no-restricted-properties` (웹 `src/**`, `src/lib/env.ts` 제외)
- 예시: `apps/web/src/lib/env.ts`

### C-38 이름 — 폴더·파일은 kebab-case, 컴포넌트 파일만 컴포넌트 이름 · `초안` · `예시`

- 기준: 폴더 `item-list/`. 컴포넌트 파일은 컴포넌트 이름 그대로 `ItemCard.tsx`(C-13). 훅 파일은 훅 이름 `useItems.ts`. 그 밖(유틸·스키마·상수)은 `get-items.schema.ts` · `item-utils.ts` 처럼 kebab-case.
  Next 가 정한 파일(`page.tsx` · `layout.tsx` 등)은 그대로. 앱 진입 파일 `providers.tsx` 도 Next 파일과 나란히 소문자로 둔다.
  모듈 상수는 `UPPER_SNAKE_CASE`(`MAX_TITLE_LENGTH`), 그 밖의 이름은 camelCase.
- 왜: 파일이 적은 지금 정하지 않으면 사람마다 케이스가 갈라지고, 나중에 맞추려면 import 를 전부 고쳐야 한다.
- 예시: `apps/web/src/lib/api/api-error.ts` · `apps/web/src/lib/query/get-query-client.ts`

### C-41 새 라이브러리는 결정 기록을 남긴 뒤 들인다 · `초안` · `글`

- 기준: 의존성을 새로 더하는 PR 은 `docs/decisions/` 에 한 장(왜 · 대안 · 버리는 것)을 같이 올리거나, 이미 있는 결정을 가리킨다. 이미 쓰는 라이브러리로 되는 일은 새로 들이지 않는다.
- 왜: 초기 팀은 한 기능마다 비슷한 라이브러리가 하나씩 늘기 쉽다. 들인 이유가 없으면 나중에 뺄 수도 없다.

### C-54 뜻이 있는 값은 이름을 붙인다 · `초안` · `글`

- 기준: 길이 제한 · 시간 · 개수 · 상태 문자열처럼 뜻이 있는 값은 이름 붙은 상수나 유니온으로 둔다(`MAX_TITLE_LENGTH`, `'draft' | 'done'`). 한 번만 쓰는 뻔한 값(`0`, `1`, 빈 문자열)은 그대로.
- 왜: 같은 값이 여러 곳에 숫자로 흩어지면 하나만 바뀌고, 그 숫자가 무엇인지 읽는 사람이 모른다.

## 컴포넌트

### C-13 내보내는 컴포넌트는 파일당 하나, 파일 이름과 같게 · `초안` · `글`

- 기준: 그 파일에서만 쓰는 비공개 하위 컴포넌트는 같은 파일에 둬도 된다. 길어지면 C-15 가 잡는다. 파일·폴더 이름 규칙은 C-38.
- 왜: 파일 이름으로 찾을 수 있어야 한다. 못 찾으면 같은 컴포넌트를 또 만든다.

### C-14 `page.tsx` · `layout.tsx` 는 조합만 한다 · `초안` · `글`

- 기준: 상태·훅·핸들러를 넣지 않고, 기능 컴포넌트를 배치만 한다. 가능하면 서버 컴포넌트로 둔다.
- 왜: 라우트 파일에 로직이 쌓이면 테스트할 곳도, 재사용할 곳도 없어진다.

### C-15 새 파일은 300줄 · 핸들러 5개 · JSX 깊이 4 안에서 · `초안` · `글`

- 기준: **새로 만드는 파일에만** 적용한다. 기존 큰 파일을 쪼개는 일은 따로 한다 — 버그를 고치다가 쪼개지 않는다.
- 왜: 크기를 린트로 강제하면 큰 파일의 한 줄 수정이 구조 변경이 된다.

### C-55 한 컴포넌트가 두 가지 일을 맡으면 나눈다 · `초안` · `글`

- 기준: 서버 조회(C-16) · 사용자 동작(핸들러 3개 이상) · 복잡한 분기(3갈래 이상, 권한별 화면) · 폼 상태 중 **둘 이상**을 맡으면 나눈다.
  Props 가 7개를 넘으면 관심사별로 묶고(`item` · `permissions` · `actions`), 켜고 끄는 boolean props 가 3개를 넘으면 자식 조합(children · 슬롯)으로 바꾼다.
- 왜: C-15 의 크기 기준은 새 파일에만 걸리고, 크기 안에서도 일이 섞이면 고칠 때 영향이 안 보인다.

### C-16 화면 컴포넌트 안에서 `useQuery` · `useMutation` 을 직접 만들지 않는다 · `초안` · `글`

- 기준: 기능 폴더의 훅(C-26)을 부른다. 그리는 컴포넌트는 props 만 받아 그린다.
- 왜: 화면 안 쿼리는 키·실패 처리가 화면마다 갈라지고, 화면을 테스트하려면 서버를 흉내 내야 한다.

### C-17 로딩·에러·빈 상태는 위에서 끊는다 · `초안` · `글`

- 기준: `if (isPending) return …` 처럼 위에서 끊고, 값이 정해진 뒤 접근한다. `data?.list ?? []` 로 흘려보내지 않는다.
- 순서: 훅 → 계산값 → 핸들러 → early return → 그리기. 훅은 return 보다 앞에 둔다(`react-hooks/rules-of-hooks` 가 막는다) — "위에서 끊는다"는 훅 다음이다.
- 왜: 빈 배열로 흘리면 조회 실패가 "목록 없음"으로 보인다 — 사용자는 실패를 모른다.
- 예시:
  ```tsx
  const { data, isPending, isError, refetch } = useItems();
  if (isPending) return <ItemsSkeleton />;
  if (isError) return <LoadFailed onRetry={refetch} />;
  if (data.items.length === 0) return <EmptyItems />;
  return <ItemList items={data.items} />;
  ```

### C-18 `useEffect` 는 허용 목록에서만 · `초안` · `기계`(일부)

- 기준: 외부 이벤트 구독 · 타이머 · 서드파티 연결 · 포커스/스크롤 · 받아 온 값으로 폼 처음 채우기. props 가 바뀔 때 state 를 맞추는 용도는 `key` 나 계산값으로.
  사용자가 한 일(누름·제출)에 따라 할 일은 효과가 아니라 그 핸들러에서 한다. 의존성 규칙을 주석으로 끄지 않는다.
  props · state · 쿼리 데이터 배열을 직접 바꾸지 않는다(`sort` · `push` · `reverse`) — 복사본(`toSorted` · 펼치기)으로.
- 왜: 계산으로 될 것을 효과로 하면 한 박자 늦게 그려지고, 의존성 누락 버그가 생긴다.
- 기계: `react-hooks/set-state-in-effect` · `react-hooks/exhaustive-deps`(경고지만 `--max-warnings=0` 이라 막힘). 허용 목록 판단은 글.
- 예시:
  ```tsx
  // 나쁨 — 계산값을 state 로 복사
  useEffect(() => setFullName(`${first} ${last}`), [first, last]);
  // 좋음
  const fullName = `${first} ${last}`;
  ```

### C-19 중첩 삼항을 쓰지 않는다 · `초안` · `글`

- 기준: 변수로 빼거나 `Record<상태, …>` 매핑. 스타일 변형은 `cn()` 조건.
  `&&` 앞에는 boolean 만 둔다 — `count && <Badge />` 는 0 일 때 화면에 `0` 이 찍힌다. `count > 0 &&` 로.
- 왜: 3분기 이상의 중첩 삼항은 어느 조건이 어느 결과인지 읽기 어렵다.
- 예시:
  ```tsx
  const STATUS_LABEL: Record<Status, string> = {
    draft: '임시',
    open: '공개',
    closed: '마감',
  };
  return <span>{STATUS_LABEL[status]}</span>;
  ```

### C-20 메모이제이션은 기본으로 쓰지 않는다 · `초안` · `기계`(일부)

- 기준: 큰 계산·참조 안정성이 필요한 의존성일 때만 `useMemo` · `useCallback`, 쓰면 이유 주석.
- 왜: 대부분의 렌더는 충분히 싸다. 습관성 메모는 의존성 배열 실수만 늘리고 읽기 어렵게 한다.
- 기계: `react-hooks/use-memo` · `react-hooks/preserve-manual-memoization` 이 잘못 쓴 메모를 막는다. 쓸지 말지는 글.

### C-21 이름 — 핸들러는 `handle` + 동사, 이벤트 props 는 `on` + 동사, named export · `초안` · `글`

- 기준: 주 동작이 하나면 `handleSubmit`, 둘 이상이면 명사까지(`handleDeleteItem`). 받는 쪽 props 는 `onSubmit` · `onDeleteItem`. Props 타입 이름은 `<컴포넌트>Props`.
  Next 라우트 파일(`page` · `layout` 등) 밖은 named export.
  핸들러는 한 줄이면 그 자리에(`onClick={() => setOpen(true)}`), 두 줄 이상 · 비동기 · 여러 상태를 바꾸면 `handle…` 함수로 뺀다.
- 왜: default export 는 가져오는 쪽이 아무 이름이나 붙여 사용처를 검색할 수 없다.

### C-22 모달은 부모가 "대상이 있으면 열림"으로 연다 · `초안` · `글`

- 기준: `const [target, setTarget] = useState<Item | null>(null)` — 열림 여부와 대상을 따로 들지 않는다.
- 왜: 둘을 따로 들면 "열렸는데 대상이 없음" 상태가 생긴다.
- 예시:
  ```tsx
  const [deleting, setDeleting] = useState<Item | null>(null);

  return (
    <>
      <ItemList onDeleteItem={setDeleting} />
      {deleting !== null && (
        <DeleteDialog item={deleting} onClose={() => setDeleting(null)} />
      )}
    </>
  );
  ```

## 서버 데이터 · 상태

### C-51 응답 타입은 Zod 스키마에서 꺼낸다 · `초안` · `글`

- 기준: 서버 응답은 Zod 스키마로 정의하고 타입은 `z.infer` 로 꺼낸다. 응답 모양을 `interface` 로 손으로 쓰지 않는다.
  스키마는 기능 폴더 `api/` 에, 엔드포인트 하나에 파일 하나 — `features/<도메인>/api/get-items.schema.ts`. 여러 엔드포인트가 같이 쓰는 조각(enum 등)만 따로 모은다.
  스키마는 `export` 한다 — 테스트 데이터도 같은 스키마로 만든다(C-45).
- 왜: 손으로 쓴 타입과 스키마가 두 벌이면 하나만 고쳐도 조용히 어긋난다. 엔드포인트마다 파일이 나뉘어야 서버 변경이 어디에 닿는지 보인다.
- 결정: `docs/decisions/0001-zod-and-react-hook-form.md`
- 예시:
  ```ts
  // features/items/api/get-items.schema.ts
  export const itemSchema = z.object({ id: z.string(), title: z.string() });
  export const getItemsSchema = z.object({ items: z.array(itemSchema) });
  export type Item = z.infer<typeof itemSchema>;
  ```

### C-52 서버 API 는 `@/lib/api` 의 `api` 로만 부른다 · `초안` · `예시`

- 기준: 컴포넌트 · 훅에서 `fetch` 를 직접 부르지 않는다. `api.get(path, schema, { signal })` 처럼 응답 스키마를 꼭 넘기고, React Query 의 `signal` 을 넘긴다. 실패는 `ApiError` 로 온다.
- 왜: 주소 조립 · 시간 제한 · 재시도할 실패 구분 · 응답 검사를 한 곳에서 한다. 직접 `fetch` 하면 그중 하나씩 빠진다.
- 예시: `apps/web/src/lib/api/client.ts` (`api` 위 JSDoc 의 `queryFn` 예)

### C-23 쿼리 키는 키 함수 하나로 만들고, 조회와 무효화가 같이 쓴다 · `초안` · `글`

- 기준: 무효화에서 키 문자열을 다시 치지 않는다. 데이터 가공은 `select` 에서.
- 왜: 키 하나만 틀려도 캐시가 안 지워지는데 타입이 못 잡는다.
- 기계: `@tanstack/query/exhaustive-deps` 가 키에 빠진 값을 막는다. 키 함수를 한 곳에 두는 것은 글.
- 예시:
  ```ts
  const itemKeys = {
    all: ['items'] as const,
    detail: (id: string) => ['items', id] as const,
  };
  // 조회: queryKey: itemKeys.detail(id) · 무효화: invalidateQueries({ queryKey: itemKeys.all })
  ```

### C-24 토스트·이동·무효화는 mutation 콜백에서 · `초안` · `글`

- 기준: 기본은 `onSuccess` · `onError`. 앞이 실패하면 뒤를 보내면 안 되는 연속 요청만 핸들러에서 `await mutateAsync` + `try/catch`.
  저장이 바꾼 데이터를 보여 주는 쿼리는 `onSuccess` 에서 무효화한다 — 빠지면 저장 뒤에도 화면이 옛 값을 그린다.
- 왜: 핸들러와 콜백에 나눠 쓰면 성공·실패 처리가 두 곳으로 갈라진다.

### C-25 저장 실패는 화면에 닿는다 · `초안` · `글`

- 기준: 토스트 · 배너 · 화면의 `isError` 중 하나. 알리지 않는 게 맞으면 어디서 대신 처리하는지 주석.
- 왜: 서버가 거부했는데 화면이 그대로면 사용자는 저장된 줄 안다.

### C-26 쿼리·뮤테이션은 기능 폴더 한 파일에 모은다 · `초안` · `글`

- 기준: 키 함수 · 조회 · 뮤테이션 훅을 기능마다 한 파일에. 파일 이름과 모양(쿼리 옵션 팩토리 여부)은 보류 "쿼리 훅 모양" — 첫 API 연동 PR 에서 정한다.
- 왜: 키와 무효화가 한 파일에 있어야 C-23 이 지켜진다.

### C-27 전역 상태 스토어 없이 시작한다 · `초안` · `글`

- 기준: 서버 값은 React Query, 화면 값은 `useState` · URL 파라미터 · Context. 여러 화면이 깊게 공유하는 값이 생기면 그때 논의한다.
- 왜: 서버 값을 스토어에 복사하면 캐시가 두 벌이 되고 서로 어긋난다.

### C-28 권한은 서버 값을 믿고, 분기는 순수 함수로 뺀다 · `초안` · `글`

- 기준: 클라이언트에서 역할을 다시 계산하지 않는다. "이 버튼을 보이나" 같은 분기는 `canXxx(…)` 순수 함수 + 단위 테스트. 그 테스트는 소스를 한 줄 깨뜨려 실패하는지 확인한다(C-46).
- 왜: 버튼 숨김은 편의이지 보안이 아니다. 컴포넌트 안 분기는 테스트하기 어렵다.
- 예시:
  ```ts
  // utils.ts — 서버가 준 값만 보고 판단
  export const canEditItem = (item: Item, me: Me) =>
    item.ownerId === me.id && item.status !== 'closed';
  ```

### C-53 보안 경계 — 저장한 링크와 남이 쓴 글을 그대로 믿지 않는다 · `초안` · `글`

- 기준:
  - 밖으로 나가는 링크는 `target="_blank"` 와 함께 `rel="noopener noreferrer"`.
  - 사용자가 넣은 · 서버가 받아 온 URL 은 `http:` · `https:` 만 링크·이미지로 쓴다(`javascript:` · `data:` 차단). 검사는 한 곳(순수 함수 + 단위 테스트)에서.
  - 사용자·외부에서 온 글은 HTML 로 실행하지 않는다 — `dangerouslySetInnerHTML` 을 쓰지 않고, 꼭 필요하면 정화(sanitize)한 뒤 이유 주석.
  - 이 분기는 C-46 대로 소스를 깨뜨려 테스트가 실패하는지 확인한다.
- 왜: 링크를 저장하고 다시 보여 주는 서비스라 남이 만든 주소와 본문이 그대로 화면에 들어온다. 한 번 뚫리면 다른 사용자의 데이터에 닿는다.

## 화면

### C-29 새 화면은 목적에서 구조로 — 배치는 그다음 · `초안` · `글`

- 기준: 새 화면을 만들거나 구조를 바꿀 때, 코드 전에 ① 요구 사항 ② 목적 ③ 가장 중요한 것 ④ 구조 ⑤ 흐름을 적어 확인받는다. 디자인이 있으면 디자인이 이것을 대신한다.
- 왜: 목적 없이 배치부터 바꾸면 같은 화면을 여러 번 다시 짜게 된다.

### C-30 조건부 클래스는 `cn()` 으로 합친다 · `초안` · `예시`

- 기준: 템플릿 문자열로 클래스를 이어 붙이지 않는다. 겹치는 Tailwind 클래스는 `cn()` 이 정리한다.
- 예시: `apps/web/src/lib/cn.ts`

### C-31 디자인 시스템 전까지 Tailwind 스케일을 먼저 · `초안` · `글`

- 기준: 임의값(`w-[13px]`)보다 스케일 값. 디자인 토큰이 생기면 이 기준을 토큰 기준으로 바꾼다.
- 왜: 임의값이 쌓이면 나중에 토큰으로 옮길 때 하나하나 판단해야 한다.

### C-32 클래스 순서는 Prettier 가 정렬한다 · `초안` · `기계`

- 기계: `prettier-plugin-tailwindcss` — 손으로 정렬하지 않는다.

### C-42 누르는 것은 `<button>` · `<a>` 로, 아이콘만 있으면 이름을 붙인다 · `초안` · `기계`

- 기준: `<div onClick>` 을 쓰지 않는다. 이동은 `<Link>`, 동작은 `<button type="button">`. 글자 없는 아이콘 버튼은 `aria-label`.
- 왜: `div` 는 키보드·스크린리더로 누를 수 없고, 이름 없는 아이콘 버튼은 "버튼"으로만 읽힌다. 셀렉터(C-36)도 못 찾는다.
- 기계: `jsx-a11y/no-static-element-interactions` · `click-events-have-key-events` · `control-has-associated-label` · `anchor-is-valid` 등 (`packages/eslint-config/next.mjs`, 웹 `src/**/*.tsx`).
- 예시:
  ```tsx
  <button type="button" aria-label="삭제" onClick={handleDelete}>
    <TrashIcon />
  </button>
  ```

### C-43 포커스 표시를 지우지 않고, 글자 대비는 4.5:1 이상 · `초안` · `글`

- 기준: `outline-none` 을 쓰면 `focus-visible:` 로 대신 보이는 표시를 준다. 본문 글자와 배경의 대비는 4.5:1 이상(큰 글자 3:1). 색은 디자인 토큰이 생기면 토큰 기준으로 본다.
  입력 칸은 `<label>` 과 연결한다(`htmlFor` · 감싸기). 저장 결과 · 처리 상태처럼 화면을 보지 않아도 알아야 하는 바뀌는 안내는 `aria-live` 영역에 둔다.
- 왜: 포커스 표시가 없으면 키보드로 어디에 있는지 모른다. 옅은 회색 글자는 밝은 화면·야외에서 안 읽힌다.

## 테스트

각 층은 다른 질문에 답한다. **같은 동작을 여러 층에서 겹쳐 보지 않고, 믿을 수 있는 가장 싼 층에서 한 번 본다.**

| 층         | 답하는 질문                      | 도구                                          | 양        |
| ---------- | -------------------------------- | --------------------------------------------- | --------- |
| 단위       | 이 **로직**이 맞나 (분기·경계값) | Vitest                                        | 빠름·많이 |
| 통합(화면) | 조각이 **연결되고 그려지나**     | Vitest + Testing Library                      | 중간      |
| E2E        | **진짜 시스템**에서 흐름이 도나  | Playwright (desktop · mobile · mobile-webkit) | 느림·적게 |

### C-44 테스트를 둘 층은 "무엇이 깨질 수 있나"로 고른다 · `초안` · `글`

- 기준: 아래 순서로 묻고 처음 맞는 층에 둔다.
  1. 순수 로직·분기 판단인가 → 단위
  2. 데이터에 따라 그려지는 것·연결인가 → 통합(화면)
  3. 진짜 시스템이 있어야만 깨지는가(아래 C-37 목록) → E2E
  4. 막으려는 게 외부 부작용(결제·메일)인가 → 그 경계만 흉내 내고 나머지는 진짜로
- 왜: 층을 잘못 고르면 느린 테스트가 늘거나(E2E 남발), 진짜 통합 문제를 못 잡는다(전부 목).

### C-33 테스트는 소스 옆 `*.test.ts(x)` 에, E2E 만 `e2e/` 에 · `초안` · `예시`

- 기준: `__tests__/` 폴더를 만들지 않는다. 단위·통합은 폴더로 나누지 않고 내용(무엇을 흉내 내나)으로 구분한다.
- 왜: 소스와 테스트가 떨어져 있으면 고칠 때 테스트를 못 본다.
- 예시: `apps/web/src/lib/cn.test.ts` · `scripts/agent-hooks/guard.test.mjs`

### C-34 새 테스트 파일 첫 주석에 "잡으려는 실패"를 적는다 · `초안` · `예시`

- 기준: 한 문장으로. 한 문장으로 못 쓰면 그 테스트는 필요 없거나 층이 틀렸다. 한 테스트가 두 실패를 섞으면 나눈다. 기존 테스트에는 소급하지 않는다.
- 예시: `scripts/agent-hooks/guard.test.mjs`

### C-46 좋은 테스트는 버그엔 실패하고, 동작이 같은 리팩터엔 살아남는다 · `초안` · `글`

- 기준: 쓰기 전에 두 가지를 묻는다 — (a) 실제 버그가 생기면 실패하나 (b) 동작을 바꾸지 않는 리팩터에도 통과하나. 하나라도 아니면 안 쓰거나 다시 쓴다.
  - 구현을 따라 쓰지 않는다 — "`setState` 가 불렸나" 대신 화면·반환값으로 본다.
  - 경계를 너무 많이 흉내 내지 않는다 — 흉내 낸 응답이 실제와 어긋나면 초록인 채 운영이 깨진다.
  - 의심되면 소스를 한 줄 일부러 깨뜨려 그 테스트가 실패하는지 본다. **권한·금액·되돌릴 수 없는 분기(C-28)와 보안 경계(C-53)는 반드시.**
  - 분기 하나를 보려고 흉내를 3개 넘게 쌓아야 하면, 그 분기를 순수 함수로 빼라는 신호다.
- 왜: 커버리지 %는 목표가 아니다. 숫자를 좇으면 아무것도 못 잡는 테스트가 쌓인다 — 테스트 없는 위험 코드를 찾는 바닥으로만 쓴다.

### C-47 꼭 쓰는 테스트와 생략해도 되는 테스트 · `초안` · `글`

- 꼭 쓴다 (하나라도 해당하면):

  | 대상                                            | 왜                                        |
  | ----------------------------------------------- | ----------------------------------------- |
  | 여러 곳에서 가져다 쓰는 공통 코드(유틸·훅·부품) | 고치면 영향이 넓다                        |
  | 응답·폼 Zod 스키마                              | 서버 계약을 지키는 마지막 줄              |
  | 조건 분기 2개 이상                              | 분기마다 따로 확인해야 한다               |
  | 상태 전이(여러 단계 폼 등)                      | 순서·조합 실수                            |
  | 한 번 버그가 났던 로직                          | 같은 회귀를 막는다                        |
  | 저장 뒤 무효화(C-24)                            | 통합(화면)에서 저장 뒤 목록이 바뀌는지    |
  | 보안 경계(C-53)                                 | 뚫리면 되돌릴 수 없다                     |
  | 새 기능                                         | 기능과 함께 쓴다(나중에 몰아 쓰지 않는다) |

- 생략해도 된다: props 를 넘기기만 하는 감싸기 컴포넌트 · 라이브러리에 맡기기만 하는 코드 · 여러 화면을 건너는 흐름(→ E2E 에서).
- 메모: 11-23 회의에서 "테스트 기준은 개발하며 정한다"고 한 항목의 후보안이다. 리뷰에서 고친다.

### C-35 무엇을 흉내 낼지는 잡으려는 실패로 정한다 · `초안` · `글`

- 기준:

  | 잡으려는 실패                                        | 흉내 내는 것                                |
  | ---------------------------------------------------- | ------------------------------------------- |
  | 그리기 · 누르기 · 접근성 · 분기 로직                 | 없음 — 순수 함수나 props 로 (API 흉내 0)    |
  | 응답 모양 · 파싱 · 에러 분기 (서버 계약)             | 네트워크 층(MSW) + 스키마로 만든 응답(C-45) |
  | 협력자를 불렀나 · 후속 동작(호출 인자, 성공 뒤 이동) | 훅·API 함수 (`vi.mock`)                     |
  - 기본은 싼 흉내(`vi.mock`)다. 네트워크 층 흉내는 잡으려는 **계약 위험을 한 문장으로 쓸 수 있을 때만**, 쓰면 그 이유를 파일에 한 줄.
  - MSW 는 아직 들이지 않았다 — 처음 필요해지면 C-41 결정 기록과 함께 들인다.

- 왜: "안전하게 다 MSW" 같은 기준 없는 선택이 테스트를 제각각으로 만든다. 잡으려는 실패와 상관없는 층을 흉내 내면 구현을 따라 깨지기만 한다.

### C-45 응답 모양 테스트 데이터는 손으로 적지 않고 스키마로 만든다 · `초안` · `글`

- 기준: 훅·API 함수를 흉내 내면 실제 Zod 파싱을 건너뛴다 — 그때 손으로 적은 데이터가 곧 계약이 되어 실제 응답과 조용히 어긋난다. 응답 모양 데이터는 응답 스키마를 통과시켜(`Schema.parse(입력)`) 만든다.
  - 덮어쓸 값은 서버가 보내는 **입력 모양**으로 준다. 스키마에 `transform` 이 있으면 입력과 결과가 다르다.
  - 스키마는 `export` 해서 테스트가 같은 스키마를 쓴다.
  - Zod 객체는 모르는 키를 조용히 버린다 — 덮어쓴 키에 오타가 있어도 테스트가 모른다. 공용 도우미는 덮어쓴 키가 스키마에 있는지 따로 확인한다.
  - 공용 도우미(`src/test-utils`)는 첫 API 테스트를 쓸 때 만든다.
- 옮기지 않아도 되는 경우: 한두 필드짜리 작은 흉내 · 반환 타입이 이미 누락을 잡는 곳 · 스키마 밖 입력을 일부러 넣어 방어를 보는 테스트. (`as unknown as T` 로 맞춘 흉내는 보호가 아니다 — C-03)
- 왜: 손으로 적은 응답 데이터는 화면이 읽는 필드와 어긋나도 테스트가 초록이다.

### C-37 E2E 는 진짜 시스템에서만 잡히는 것만 · `초안` · `예시`

- 기준: 라우팅 · 로그인/세션 · 하이드레이션 · 실제 API 계약과 응답 모양 · 환경 설정 · 누름 → 이동 → 그리기 연결 · 브라우저 고유 동작(스크롤 · 클립보드 · 뷰포트) · 웹뷰(WebKit) 차이. 이게 아니면 낮은 층으로 내린다.
  - 핵심 사용자 흐름(happy path) 위주로 적게. 앱이 뜨는지 보는 연기 시험 하나는 둔다(하이드레이션 · 환경 설정).
  - **외부 경계만 흉내 낸다** — 결제 · 메일 · 외부 로그인 · 시간 · 랜덤. 우리 서버의 정상 응답을 흉내 내 특정 상태를 만들지 않는다 — 그러려면 그 테스트는 낮은 층으로 간다.
  - 실데이터로 만들기 어려운 상태의 분기는 순수 함수로 빼 단위로, "그 상태에서 누르면 맞는 동작을 부르나"는 통합(화면)에서 훅을 흉내 내 본다.
- 왜: E2E 는 느리고 흔들린다. E2E 에서 응답을 통째로 흉내 내면 E2E 만 잡을 수 있는 진짜 통합을 버리게 된다.
- 예시: `apps/web/e2e/home.spec.ts` (연기 시험)

### C-48 리팩터 전에 지금 동작을 테스트로 묶는다 · `초안` · `글`

- 기준: 테스트 없는 코드는 리팩터하지 않는다. ① 지금 동작을 묶는 테스트를 먼저 쓰고 ② 초록인 채로 고치고 ③ 그대로 초록이면 동작이 같다는 증명. 옮길 때는 다시 쓰지 않고 그대로 옮긴다. 리팩터는 기능 변경과 다른 커밋으로(C-15).
- 왜: 테스트 없이 구조를 바꾸면 무엇이 달라졌는지 아무도 모른다.

### C-49 테스트 실행에 경고·에러 출력이 없어야 한다 · `초안` · `글`

- 기준: `pnpm test` 의 stderr 경고·에러는 0건. 일부러 에러를 던지는 테스트는 `console.error` 를 잠깐 막고 되돌린다.
  ```ts
  beforeEach(() => vi.spyOn(console, 'error').mockImplementation(() => {}));
  afterEach(() => vi.restoreAllMocks());
  ```
- 왜: `act` 경고 같은 출력이 쌓이면 진짜 문제가 그 사이에 묻힌다.

### C-50 쿼리 훅 테스트는 재시도를 끈 QueryClient 로 감싼다 · `초안` · `글`

- 기준: `renderHook` + 테스트마다 새 `QueryClient({ defaultOptions: { queries: { retry: false } } })` 로 감싸고 `waitFor` 로 기다린다. 이 감싸기는 첫 훅 테스트 때 `src/test-utils` 에 공용으로 둔다.
- 왜: 재시도가 켜져 있으면 에러 케이스가 느려지고 흔들리며, 클라이언트를 테스트끼리 나눠 쓰면 캐시가 다른 테스트로 샌다.

### C-36 셀렉터는 `getByRole` · 이름이 먼저 · `초안` · `글`

- 기준: `getByRole` → `getByLabelText` → `getByText` 순. `data-testid` 는 마지막.
- 왜: 셀렉터가 곧 접근성 검사가 된다 — 역할·이름이 없으면 못 찾는다(C-42).
